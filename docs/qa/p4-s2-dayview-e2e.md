# P4-S2 Day view browser integration evidence

`tests/e2e/day-view.spec.ts` runs 10 Playwright checks against the real Day view bundle and a synthetic ledger served by `runDaemon` with fake Swift helper frames. Because the daemon writes only a TCP token hash to `run/web.json`, a separate authenticated `startApiServer` relays the browser's four resource calls to the daemon's real UDS. This proves UI → browser HTTP → relay → daemon UDS behavior, including output validation and deletion. It does **not** prove UI → daemon TCP authentication or WKWebView token delivery. Those require the approved web-session contract described in `p4-integration-contract-gaps.md`.

The checks cover the four YAML Day view scenarios: day overview/Sources rendering, a single `read` call with script-like evidence kept as text, expired evidence linking to its summary, and an empty day with adjacent dates. Extra checks cover summary hash scrolling, previous/next and Settings navigation, today-only Clear confirmation and reload, and unauthenticated 401 from both daemon and relay TCP listeners. The empty-day case also injects a literal `null` RPC result through the relay; the current daemon returns `{markdown:null}` for a missing valid day, and both are parsed by the UI.

Initial integrated verification on `phase-3-recall` (historical): `bun test` 696 pass, 0 fail, 4,307 assertions across 68 files; `npx tsc --noEmit` exit 0; `npx biome check .` 183 files clean; `bun run build:web` 116 modules; `swift test --package-path apps/side-mac` 136 SideCaptureKit and 10 SideApp tests, 0 failures. P4-S2-T2 remained open at that point until the browser could use the actual daemon TCP session. P4-S2-V subgates could be judged separately from the specific file and endpoint checks; app-level navigation and external browser handoff were unobserved in that run. Later evidence is recorded in `docs/qa/p4-direct-tcp-e2e.md` and `docs/qa/p4-s3-external-links.md`.
